# オリジナル画像形式「LIVF」を作っている話

最近、**LIVF（Layered Image Variant Format）** というオリジナルの画像形式を作っています。  
LIVFはキャラクターの立ち絵のような、複数のレイヤーや差分を持つ画像を扱うための形式です。

拡張子は`.livf`で、現在GitHubで仕様やC#の参照実装を開発しています。

**リポジトリ：[Karotte3500500/LIVF🥕](https://github.com/Karotte3500500/LIVF)**

まだ開発途中ですが、最初の仕様となるv0.1.0がある程度固まり、実際の立ち絵を使ったサンプルも作れるようになってきました。

今回は、そもそもなぜLIVFを作ろうと思ったのかと、現在どのような形式になっているのかについて紹介します。

<br/>

# PSDでの立ち絵管理

これまでゲームを作るとき、キャラクターの立ち絵にはPSDを多く使っていました。  
PSDはレイヤー構造をそのまま保持できるため、

```text
face
├─ eyes
│  ├─ normal
│  ├─ half
│  └─ close
├─ mouth
│  ├─ normal
│  ├─ smile
│  └─ open
└─ eyebrows
   ├─ normal
   ├─ worried
   └─ angry
```

といった形で、一つのファイルに複数の差分をまとめることができます。

ゲームやWebからPSDを読み込み、レイヤーの表示・非表示を変更することもできるので、レイヤー構造を持った画像をアプリケーションで扱うこと自体は特に問題ありません。

しかし、複数の開発をしているとPSDだけでは少し不便に感じることがありました。  
何が困っていたのかというと、**PSDが持っているのはレイヤー構造まで**という点です。

例えば、
***``` 笑顔 = 目の差分2 + 口の差分3 + 眉の差分1 ```***
という表情を作りたいとします。

PSDには目や口、眉のレイヤーは入っていますが、「この組み合わせを笑顔として使う」という情報は入っていません。
そのため、ゲーム側でレイヤーの組み合わせを管理する必要があります。

## 差分の情報がアプリケーション側にある

一つのゲームだけで使うのであれば、この方法でも特に困りません。  
ゲーム側で、

```text
smile
├─ eye2
├─ mouth3
└─ eyebrow1
```

のような組み合わせ情報を持っておけば、笑顔を表示できます。  
しかしながら、このキャラクターを別のアプリケーションでも使おうとすると少し面倒になります。

例えば、Unityで作ったゲームとWebサイトの両方で同じPSDを使うとします。  
このとき、Unity側で定義した
***``` 笑顔 = 目の差分2 + 口の差分3 + 眉の差分1 ```***
という情報はPSDには入っていないので、Web側でも、同じ組み合わせをもう一度定義する必要があります。

もし設定を誤れば、同じキャラクターのファイルでも、
**Unityで表示される笑顔 ≠ Webで表示される笑顔**
ということが起こり得ます。
つまり、同じ画像ファイルを使っているのに、
その画像がどのような差分を持っているのかはアプリケーション側に依存している状態なのです。

そこで、レイヤーだけでなく、**レイヤーの組み合わせも画像ファイル側で管理できればいいのではないか**と考えました。

これがLIVFを作ることになった切っ掛けでした。
<br/>

# 排他的なレイヤーも欲しい

もう一つ欲しかったのが、レイヤー同士の排他関係です。  
例えば目に、
```text
eyes
├─ normal
├─ half
└─ close
```
という3種類の差分があったとします。

目の差分が複数表示されていたらもちろんおかしいので、基本的には、この中から一つだけを表示したいですよね。
しかし、PSDは普通のレイヤー構造なので、そのままだと3枚すべてを同時に表示することができますし、
排他的な表示をしたいという意図も残りません。

もちろんこれも、ゲーム側で
```text
closeを表示する
↓
normalとhalfを非表示にする
```
という処理を書けば解決できます。

ただ、これも「このレイヤーたちは同時に表示しない」という情報をアプリケーション側が知っていることになります。
そのため、この関係もファイル側に持たせたいと考えました。

そこでLIVFでは、Folderに`selectionMode`という設定があります。

```text
eyes                 exclusive
├─ normal
├─ half
└─ close
```

`exclusive`の場合は、子Nodeの中から一つのレイヤーだけを表示できます。  
`close`を表示すると、それまで表示されていた`normal`などは自動的に非表示になります。

一方で、アクセサリーのように複数を同時に表示したい場合は、

```text
accessories           multiple
├─ glasses
├─ hat
└─ necklace
```

のように`multiple`を使います。

この辺りは、最初にLIVFを考えたときから欲しかった機能です。

<br/>

# LIVF形式

このような問題を解決するために作り始めたのがLIVFです。  
現在のv0.1.0ではZIPをベースにしたコンテナ形式になっており、
内部は以下のような構造です。

```text
character.livf
├─ manifest.json
├─ thumbnail.png
└─ images/
   ├─ body.png
   ├─ eye_normal.png
   ├─ eye_close.png
   ├─ mouth_normal.png
   └─ mouth_smile.png
```

画像本体はPNGとして格納し、レイヤー構造や差分に関する情報を`manifest.json`に記録しています。

manifestの最上位は、現在このようになっています。

```json
{
  "livfVersion": "0.1.0",
  "metadata": {},
  "canvas": {},
  "defaultState": "character.default",
  "nodes": [],
  "states": [],
  "stateGroups": []
}
```

`nodes`にはLayerやFolder、`states`には差分の組み合わせ、`stateGroups`には関連するStateの情報が入ります。

<br/>

# State

先ほどの、
***``` 笑顔 = 目の差分2 + 口の差分3 + 眉の差分1 ```***
のような組み合わせをLIVFでは`State`として定義します。  

```json
{
  "id": "expression.smile",
  "name": "笑顔",
  "changes": [
    {
      "target": "face.eyes.smile",
      "visible": true
    },
    {
      "target": "face.mouth.smile",
      "visible": true
    }
  ]
}
```

そして、アプリケーションからは、以下のようにStateを指定します。

```cs
character.SetState("expression.smile");
```

こうすることで、アプリケーション側は「笑顔にするとき、どのレイヤーを表示する必要があるのか」を知る必要がありません。
組み合わせ情報はLIVFファイル側に入っているため、
UnityでもWebでも同じLIVFファイルを読み込めば、`expression.smile`は同じレイヤーの組み合わせになります。
<br/>
# State Group

Stateをまとめるために`StateGroup`という仕組みもあります。

例えば、

```text
expression
├─ normal
├─ smile
├─ angry
└─ confused
```

のように、表情に関するStateを一つのグループとして管理できます。

衣装であれば、以下のようになります。

```text
costume
├─ normal
├─ school
└─ winter
```

表情と衣装は別のStateGroupなので、

```text
笑顔 + 冬服
```

のような組み合わせもできます。

現在想定しているC#のAPIでは、

```csharp
character.SetGroupState(
    "expression",
    "expression.smile"
);
```

のように操作します。

まだ参照実装は開発途中なのでAPIは今後変わる可能性がありますが、アプリケーションからレイヤーを直接操作するだけでなく、「表情」や「衣装」といった単位で操作できるようにしたいと考えています。

<br/>

# Default State

仕様を考えている中で、特に重要になったのがDefault Stateです。

LIVFでは、StateやStateGroupだけでなく、アプリケーションから直接Layerの表示状態などを変更することもできます。
そのため、使っているうちに、
```表情を変更 → メガネを非表示 → 頬染めを表示 → 口だけ個別に変更```
のように、最初には想定していなかった組み合わせになることもあります。

ここで欲しかったのが、**今どんな状態になっていても、想定した状態へ必ず戻れる** 仕組みです。  
この**想定した状態**と**必ず戻れる**の両方は重視していました。

例えば、単純に`character.default`というStateを用意するだけでは十分ではありません。  
Stateは、定義されている変更だけを現在の状態へ適用します。

そのため、
```メガネを非表示 → 頬染めを表示```をしたあとに、
```目を通常へ戻す → 口を通常へ戻す```
というDefault用のStateを適用しても、メガネや頬染めの状態がそのまま残ってしまう可能性があります。

これでは、操作する前の状態によって結果が変わってしまいます。

そこで、LIVFのDefault Stateではそうならないようにしています。

ファイルを読み込む際に、
- Nodeの初期状態
- Folderの`defaultChild`
- StateGroupの`defaultState`
- ファイル全体の`defaultState`

などから、制作者が想定した標準状態を一度構築します。   
そして、その完成した状態を`Default Snapshot`として保持します。

その後、どれだけ状態を変更しても、

```csharp
character.ResetToDefault();
```
を実行すれば、現在の状態に関係なくDefault Snapshotへ復元します。

また、その結果として、ファイル読み込み直後がResetToDefault()実行直後の状態になることも保証されます。
ただ、これはDefault Stateの目的そのものではなく、**常に想定した状態へ戻れることを保証した結果**です。

Stateが「現在の状態に変更を加える仕組み」だとすれば、Default Stateは「現在の状態に関係なく、基準となる状態へ戻す仕組み」として分けて考えています。  
この辺りは仕様を考える中でもかなり悩んだ部分ですが、LIVFの状態管理では重要な仕組みになったと思っています。

<br/>

# PSDとの違い

LIVFはPSDの代わりになる画像編集形式を目指しているわけではありません。  

PSDはイラスト制作のための形式として非常に多くの機能を持っています。
LIVFでPhotoshopの機能を全部再現しようとすると、それこそPhotoshopをもう一つ作るような話になってしまいます。

そのため、制作は今まで通りPSDなどで行い、

```text
PSDなどで立ち絵を制作
↓
LIVFへ変換
↓
ゲームやWebで利用
```

という使い方を想定しています。

PSDが主にレイヤー構造を持っているのに対して、LIVFでは、

- このFolderは排他的なのか
- どのレイヤーの組み合わせが一つの差分なのか
- どのStateが表情や衣装に属するのか
- 初期状態は何なのか

といった、実際にアプリケーションから利用するときに必要になる情報も一緒に持たせます。

<br/>

# Live2Dとの違い

LIVFについて説明すると、Live2Dに近いものを想像するかもしれません。

ただ、LIVF v0.1.0では、

- ボーン
- メッシュ変形
- 物理演算
- アニメーション

などには対応していません。

今のところ、LIVFが対象にしているのは静止画像の差分のみであり、
既に描かれているレイヤーを組み合わせて表示することに特化しています。

将来的にアニメーションなどをどうするかは分かりませんが、少なくとも現在のLIVFでは、Live2Dのような仕組みを作ることは目的にしていません。

<br/>

# 実際にLIVFファイルを作って試す

仕様だけ作っていても本当に使えるのか分からないので、実際の立ち絵を使ったテストもしています。

現在はLIVFのマスコットキャラクターである「Liviちゃん」を使って、v0.1.0のサンプルを作っています。
このサンプルは目、虹彩、まつ毛、眉、口、頬染めなど複数の差分を持っており、LIVFの機能を一通り試せるようにしています。

実際の素材で試す中で、仕様だけ考えていたときには気付かなかったケースも結構出てきます。
例えば、虹彩本体には複数の差分がありますが、その上にあるハイライトはどの差分でも表示したいです。

そのため、

```text
iris           multiple
│
├─ variants    ┐
│  ├─ normal  │exclusive
│  ├─ sanpaku │
│  └─ ...     ┘
└─ highlight
```

のような構造にすることで、

```text
虹彩の差分1枚
+
ハイライト
```

を同時に表示できるようにしています。

こういった実際の立ち絵で出てくるパターンを試しながら、仕様を確認しています。

<br/>

# C#で参照実装を作る

ファイル形式だけ決めても、実際に読み込めるプログラムがなければ使えません。  
そのため現在は、C#で参照実装を作っています。

LIVF自体は特定の言語に依存しないので、最終的にはWebならTypeScript、UnityならC#といった形で、それぞれの環境にランタイムを作れます。
最初にC#を選んだ理由の一つは、Unityで使いやすいことです。

ただし、最初からUnity専用のコードにはせず、
```text
Livf.Core
Livf.Serialization
Livf.Validation
Livf.Rendering
```
のように分けて作る予定です。

現在は最初の`Livf.Core`から実装しています。

まずは、

```text
.livf
↓
読み込み
↓
検証
↓
状態を変更
↓
描画
```

まで一通り動くところを目標にしています。

<br/>

# ファイル形式だけでは使えない

LIVFを作り始めた頃は、ファイル形式の仕様を作ることばかり考えていました。

ただ、実際にサンプルを作ってみると、
LIVFファイルとそのランタイムだけでは非常に使いづらいことに気が付きます。
どれだけ仕様を作っても、手作業でmanifestを書く必要があるなら気軽には使えません。  
そのため、現在はファイル形式以外にも、
- LIVF Editor
- PSD Importer
- CLI
- Unity Runtime
- Web Runtime
- Viewer

などを作りたいと考えています。  

特にPSD Importerはかなり重要だと思っています。
普段通りPSDで絵を制作して、そこからLIVFへ変換し、差分の情報を追加できるようになれば、
制作側の作業を大きく変えずにLIVFを使えるようになります。

また、現在のv0.1.0では通常のアルファ合成だけに対応していますが、乗算などのブレンドモードも今後追加したい機能の一つです。

ただし、v0.1.0の仕様自体は一旦固定し、こうした機能は次のバージョンとして追加する予定です。

<br/>

# 最後に

LIVFを作り始めた理由はかなり単純で、

#### 「レイヤーの組み合わせをアプリ側で毎回管理するより、画像側で持てた方が便利じゃん」

と思ったことでした。  
そこから排他的なFolderやState、StateGroup、Default Stateなどを考えていき、
今では思っていたよりもちゃんとしたファイル形式の話になってきました。

まだ仕様とサンプルができ、参照実装を作り始めたくらいなので、実際に使いやすい状態になるまではかなり先だと思います。
EditorやPSD Importerまで考えると、作りたいものもかなり残っています。

ただ、自分でファイル形式を考えて、それを実際に読み込むランタイムまで作る機会はあまりないので、かなり楽しみながら開発しています。

今後、C#の参照実装やEditorなどが形になってきたら、その辺りも記事にしていこうと思います。
