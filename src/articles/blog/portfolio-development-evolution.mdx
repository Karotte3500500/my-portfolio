# ポートフォリオサイトが開発の実験場になるまで

このポートフォリオサイトを作り始めてから、約3ヶ月が経ちました。
当初は、React.jsの勉強をしながら、自分の制作物や経歴を載せるサイトを作ることが目的でした。

一方で、Gitの履歴を振り返ってみると、
ブログ機能を追加したり、CIを導入したり、Gitの運用ルールを書いたり、Next.jsへの移行を20個近いIssueに分けたりしています。
もはや、ポートフォリオサイトを作っているというより、
このリポジトリで開発そのものを勉強している状態になっています。

本記事では、このサイトの開発目的や運用方法が、どのように変わっていったのか振り返ってみます。

<br/>

# とりあえずサイトを作る

このサイトの最初のコミットは、2026年7月7日です。

当時はHero、Works、Skills、Historyなど、ポートフォリオに欲しい機能を順番に追加していました。
Gitについても、今ほど深く考えておらず、
コミットして、必要ならブランチを作って、動いたらmainへ反映するといった流れとなっており、
ありふれた個人開発といった感じでした。

## ブログを書きたくなった

ある程度サイトが形になったところで、制作物や経歴だけでなく、開発の過程や学んだことも記録したくなりました。
そこで、ブログ機能を追加し記事を書き始めました。

しかし、記事を書くようになると少し状況が変わります。
MDX、Frontmatter、SEO、サイトマップなど、単なるポートフォリオ制作では触れなかった技術を扱うようになりました。

また、サイトマップの自動生成について調べたときには、その実装自体をブログ記事にしました。
この辺りから、サイトを作るために技術を調べ、調べた内容を記事にするために、またサイトを改良するというサイクルが生まれ、
ポートフォリオサイトが学習環境として機能し始めたのだと思います。

<br/>

# 当時のGit運用

以前の記事では、Gitについて以下の3ブランチで運用すると書いていました。

```text
main
feature
article
```

`feature`では機能開発、`article`では記事を書くという構成です。

当時は「個人開発でも本番環境と開発環境を分離できる！」と満足していました。
実際、それ以前よりはかなり安全になりました。

ただし、この方式では`feature`も`article`もずっと使い続けており、
記事を3つ書いたとしても、すべて同じ`article`ブランチで執筆することになります。

```text
Merge branch 'article'
Merge branch 'feature'
Merge branch 'main' into feature
```

実際に、上記のような履歴が結構残っています。

当時としてはこの運用方法で十分でしたし、
ぶっちゃけ、個人開発なのでこの方法が記事の執筆や開発を進めやすかったのも事実です。

しかし、この運用を大きく変える切っ掛けがインターンシップでした。

<br/>

# インターンで開発の進め方が変わった

多くのインターンでは普段の個人開発とは異なり、
チームや組織の中でIssueやPull Requestを使って開発していました。
そこで特に印象に残ったのが、
**「何を実装するか」だけでなく、「変更をどう分けるか」も考える**
ということでした。

個人開発では、自分が把握できていれば多少いろいろな変更が混ざっても困ることはありません。
一方でチーム開発では、このPRは何のための変更なのか、どこまでがスコープなのか、どう確認するべきか、
といったことを他の人にも分かるようにする必要があります。

また、インターンでは**コーディングAIを実際の開発に使うこと**も体験しました。  
それ以前もChatGPTにはかなり相談していましたが、基本的には、

```text
ChatGPTに相談する
↓
自分でコードを書く
```

という使い方でした。

コーディングAIを用いたAI駆動開発を体感したことで、
```text
作業内容を決める
↓
AIがリポジトリを読んで実装する
↓
結果を人間が確認する
```
上記のような運用方法にシフトした方が効率的だと感じました。

これは自分にとって、本当に大きな変化でした。

<br/>

# Next.jsへの移行を始める

ちょうど同じ頃、このサイトをVite + ReactからNext.jsへ移行しようと考えていました。
ただ、調べてみると想像以上に影響範囲が広いです。
React Router、MDX、localStorage、window、SEO、サイトマップなど、いろいろな部分を変更する必要があります。

流石に、
#### 「全部書き換えて、壊れたところから直せばええやろ！」
では危なそうです。

そこで、インターンで経験した開発方法を個人開発にも持ち込むことにしました。  
まず、長く使っていた`feature`と`article`をやめて、変更ごとにブランチを作るようにしました。

```text
feature/<name>
article/<slug>
fix/<name>
refactor/<name>
chore/<name>
```

そして、変更はPull Requestを通して反映します。

GitHub Actionsも追加し、lint、型チェック、buildを自動で確認するようにしました。
Next.jsへの移行自体も、一つの巨大な作業にはしていません。

現在は、

- Next.jsの最小構成
- テーマのSSR対応
- Heroのwindow依存
- App Router
- MDX
- Metadata
- sitemap
- Viteの削除

など、20個近いIssueに分割しています。

さらに、移行途中のNext.js版は`migration/nextjs`に集め、現在公開しているVite版のmainとは分離しています。

<br/>

# AIのためにAGENTS.mdを書いた

コーディングAIを使い始めると、今まで頭の中だけにあったルールを書く必要も出てきました。

例えば、
- mainで直接作業しない
- 関係ない部分をついでに修正しない
- ライブラリを勝手に追加しない
- 変更後はlintやbuildを確認する

などです。

そこで`AGENTS.md`を追加しました。
これはAI向けのルールなのですが、書いてみると、

#### 「これ、人間が開発するときにも必要なルールでは？」

となりました。

実際、最近は作業中に別のバグを見つけても、そのPRでは修正せずIssueとして残すことがあります。
以前なら「ついでに直しちゃえ」とやっていたと思います。
AIに作業を任せるために変更範囲を明確にしていたら、自分自身も変更の範囲を意識するようになったわけです。

<br/>

# どう作るか「だけ」から脱却

こうして履歴を追ってみると、この3ヶ月で興味の対象がかなり変わりました。

最初は、「どう実装するのか」という事ばかりを考えていましたが、
最近はそれだけでなく、この変更はどこまでなのか、どう分ければ安全に変更できるのか、どうすれば後から意図を追えるのか、
といったことを考えるようになりました。

ポートフォリオを作り始めたはずが、
結果的にはこのサイト自体が、Web開発やGit、AIを使った開発方法を試す場所になりました。

Next.jsへの移行が終わった後も、ブログ記事や`src/data`をフロントエンドから分離してみたいと考えています。

おそらく、このサイトは完成しません。  
今後も新しく知った技術や開発方法を、このリポジトリで実際に試していきたいです。

そして数ヶ月後にGitの履歴を見返したとき、

#### 「随分やり方変わったな……」

となっていたら面白いなと思います。
