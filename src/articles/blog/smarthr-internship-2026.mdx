SmartHRの5Daysインターンシップに参加しました。  
自分にとって人生初のインターンシップだったので、かなり不安や期待が大きかったことを覚えています。

参加する前は、「どんな技術を使うんだろう」「どんなものを開発するんだろう」と、
技術的な部分に強く興味を持っていましたし、実際に開発をする中で技術面の学びも多くありました。
一方で、それ以上に印象に残っているのは、プロダクトの作り方やチームで開発するときの考え方です。

本記事では、5日間で取り組んだ開発と、その中で印象に残ったことについて振り返ります。

<br/>

# 紙飛行機を作ってアジャイル開発を学ぶ

初日には、アジャイル開発を体験するという目的のもと、チームで紙飛行機を作るワークがありました。

ルールはおおよそ以下のようなものです。

- チーム全員が製造に参加する
- 1人が連続して行えるのは紙を1回折るところまで
- 完成した紙飛行機は一度だけテストする
- 指定された距離を飛べば出荷、失敗すれば破棄
- 最終的な出荷数を増やす

いきなり製造を始めるわけではなく、
最初に作る紙飛行機や目標数を決めたあと、

***`計画 → 製造 → テスト → 振り返り → 計画 …`***

というPDCAサイクルを何度か繰り返します。

## 「よく飛ぶ飛行機」と「量産できる飛行機」

最初のサイクルでは、インターネットで調べた「よく飛ぶ紙飛行機」の折り方を採用しました。  
実際によく飛ぶのでテストの成功率は高かったのですが、
工数が多く制作に時間がかかるため、出荷できる数は少なくなってしまいました。

そこで次は、もっと簡単な紙飛行機に変更しました。  
すると、今度はたくさん作れるようになった一方で、あまり飛ばないためテストの成功率が下がってしまい、
結果的に出荷できる数は伸びませんでした。

品質を重視すると生産量が減り、
生産量を重視すると品質が下がります。

## ダーツのような紙飛行機
このサイクルを何度も繰り返した結果、出荷数が格段に増加し、最後に作っていたものは最初に想像していた紙飛行機とはかなり違う、ダーツのような形になっていました。

![ダーツのような紙飛行機](/images/blog/smarthr-internship-2026/internship2026-08-8_2.jpg)

出来上がった紙飛行機は、レギュレーションを完璧に満たしており、製作コストは低く、テスト成功率は高いです。
一方で、**作る前では誰も考えられなかった変わった形**をしていました。

最初から最適な紙飛行機を考え抜くのではなく、
実際に作ってみて、その結果を見ながら改善していくことで、
**最初に想像していたものよりも良いものを作ることができる**
ということを体験できました。

そして、この体験はその後のアプリ開発でもかなり似ていました。

# 4人チームで社内公募アプリを開発

今回のインターンでは、4人でチームを組み、社内公募を管理するアプリケーションを開発しました。  
飛行機ワークが初日にあったため、開発期間は実質4日間です。

最初に仕様をすべて決め、その通りに作って終わるのではなく、
毎日ユーザヒアリングやスプリントレビューを行い、クライアント役の方から話を聞いたり、実際に作ったものを触ってもらったりしながら開発を進めました。

また、実装では人力でコードを書くことはほぼなく、Claude Code をかなり活用した開発を行いました。

そのため、単純にコードを書くこと以上に、何を作るのか、何を優先するのか、ユーザーが何を必要としているのか
、といった実装以外の部分を考える時間が多かったです。

## ユーザーの要求をそのまま作ればいいわけではない

最初のユーザヒアリングでは、社内公募を管理する現在の業務や、その中で困っていることについて聞きました。
そこから、クライアント役の企業では、スプレッドシートを中心に管理しており、
公募をより多くの社員が見られるようにしたいことや、属人的な作業をシステム化したいという要求を把握しました。

そこで最初は、既存の業務フローをヒアリングし、それをそのままシステムへ落とし込むところから始めました。
自分たちとしても、まずは現状を正確に理解することが必要だと考えていたからです。

しかし、実際に作ったものを触ってもらうと、
Googleカレンダーとの連携や通知、公募形式の変更など、最初のヒアリングでは出ていなかった要望も出てきました。

このとき、ユーザー自身も最初から理想の状態をすべて言語化できるわけではないのだと感じました。

クライアントにとって、実物がない状態で「どんなシステムが欲しいですか？」と聞かれても、すべてを想像するのは難しいでしょう。  
一方で、実際に画面を触ると、「ここはこうしたい」「この作業も一緒にできると嬉しい」といったものが見えてきます。

ヒアリングで聞いた要求をそのまま実装するだけではなく、
実際に使ってもらいながら、その背景にある課題を探していく必要があると感じました。

## 4日間ですべては作れない

前述しましたが、開発期間は4日間しかありません。

そのため、ヒアリングで出た要望をすべて実装することはできないため、
ユーザーに優先度を確認しながらチームでもMVPを何度も見直しました。

その中で特に重要だと考えるようになったのが、認証認可とUI・UXです。

社内公募には、誰でも見てよい情報だけでなく、
権限によって閲覧できる情報が変わる場面があります。  
そのため、

- 誰がどの情報を閲覧できるのか
- 見えてはいけない情報が見えないこと
- 自分が次に何をすればよいのか分かること

といった部分を重視しました。

短期間なので機能を削る必要はありますが、
ユーザーが安心して使うために必要な部分まで削ってしまえば、使えるプロダクトにはなりません。

この辺りは、紙飛行機ワークで経験した「単純に速く作れば良いわけではない」という話にも近かったと思います。

# チーム開発で気づいたこと

今回のインターンでは、プロダクト開発だけでなく、チーム内での自分の振る舞いについても大きな学びがありました。

チームには、自分たちの中でもかなり優秀だと感じるメンバーがいました。  
ここでは彼をAさんとします。

開発期間が短かったこともあり、自分を含めた他のメンバーは、
「Aさんに意思決定を任せた方が速いのでは？」
と考えることが多く、実際に多くの判断を任せていました。  
また、Aさんもスピードをかなり意識しており、
MVPをできるだけ小さくする方針を取っていました。

当時はこの方法でも大きな問題は起きていませんでしたし、
短期間で開発を進めるという意味では合理的だったと思います。

## 考えていることを共有していなかった

AさんのMVPを狭める進め方は確かにスピードが出ますが、
自分はUI・UXについて少し違う考えも持っていました。
しかし、Aさんの意思決定に任せた方がスムーズに進むと考え、この考えを共有しませんでした。

そんな中、1日の終わりにあるメンターの方との1on1面談の中で、
SmartHRのValueの一つでもあるHRTという考え方について話す機会がありました。  
HRTとは、

- Humility / 謙虚
- Respect / 尊敬
- Trust / 信頼

の頭文字を取ったもので、この3点を相手に対して持ってコミュニケーションを取ることを意味します。

その際、自分について、
「発言すると的を射ていることが多い一方で、考えていること自体をチームへ共有していない」
というフィードバックをいただきました。

それまで自分は、
すでにチームの方針が決まっていて開発も進んでいるのであれば、それに合わせる方が良いと考えていました。

しかし、自分が何か違う視点を持っているのであれば、
その視点を共有することで、チーム全体の力になることができますし、
発言することがチームの意思決定を遅らせるという考えはチームメンバーに対する信頼が欠けているのではないか？と考え直しました。

そこからは、
自分が考えていることも以前より積極的に共有するようになりました。

## ユーザーに判断を委ねる

自分は以前に開発した「はたちゃ」での経験から、
今回のプロダクトでもUI・UXはかなり重要になると感じていました。
ただ、当初はAさんの方針とは少し違っていたため、
チーム全体にはあまり共有せず、別のメンバーであるBさんに話す程度でした。

1on1面談のフィードバックを受けたあと、
この考えをチーム全体にも共有しました。

そこでAさんともUXについて話すことができたのですが、
今度はAさんとBさんの意見が割れました。  
面白かったのが、二人とも、

#### 「クライアントが求めているのは自分の方針だ」

と考えていたことです。  
しかし、チーム内だけで議論していても、本当にユーザーがどちらを求めているのかは分かりません。
そこで、考えている案をユーザーへ提示して、実際に確認してみることを提案しました。

結果として、ユーザーの意見を聞いた上でスムーズにチームの方針を決めることができました。

このときに感じたのは、
誰かの考えが間違っていたとか、正しかったということではありません。
それぞれの視点には価値があり、それらを尊重し、協力して進めることが重要だと感じました。

それぞれのメンバーに独自の始点があり、
自分もこれまでの開発経験から持っていた視点があります。  
誰か一人だけでは拾えない部分があるからこそ、複数人で開発する意義があるのだと体感しました。

そして、意見が割れたときには、
チームの中だけで「どちらが正しいか」を決めるのではなく、ユーザーに確認する方法もありまず。

考えていることを共有するようになったことで、
チーム内での議論も増え、プロダクトの方向性についても以前より多く話せるようになりました。

# 技術だけではなかった5日間

インターンに参加する前は、
インターンシップに対して「実際の会社で開発を経験する場所」というイメージを持っていました。

実際、Claudeを使った開発や、短期間でのプロトタイピング、認証認可、UI・UXなど、技術的にも多くの経験ができました。

ただ、それ以上に印象に残っているのは、

- ユーザーの要求をそのまま作れば良いわけではないこと
- 最初から理想のプロダクトが分かるとは限らないこと
- 短期間だからこそ、何を作らないかを考える必要があること
- 自分が持っている考えをチームへ共有すること

といった部分です。

5日間という短い期間でしたが、
プロダクトの作り方だけでなく、自分がチームの中でどう動くのかについても考える切っ掛けになりました。

<br/>

# 最後に

初日の紙飛行機ワークでは、
最初に自分たちが良いと思っていた紙飛行機と、最後に作っていたものはまったく違う形になっていました。

実際の開発でも、最初に考えていたプロダクトと、
ヒアリングやレビューを重ねたあとのプロダクトは少しずつ変わっていきました。

そして、自分自身の開発に対する考え方も、5日間の中でかなり変わったと思います。

今回学んだことは、今後の個人開発やチーム開発でも実際に試していきたいです。

SmartHRのみなさん、そして5日間一緒に開発したチームのみんな、本当にありがとうございました。
